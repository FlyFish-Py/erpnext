# BUG-003：系统清单列表的列翻译未生效（格式化器被覆盖）

| 项目 | 内容 |
|---|---|
| 日期 | 2026-07-03 |
| 严重级别 | 低（界面美化功能未生效，无业务影响） |
| 关联 | 明达翻译通道 · 系统清单列表列翻译（全局脚本） |

## 1. 现象

部署全局脚本后，「构建 → 单据类型」列表的"模块"列仍显示英文（CRM、Manufacturing、Accounts……），翻译格式化器未生效。

## 2. 根因

时序覆盖问题：mingda 的全局脚本（`app_include_js`）在**桌面启动时**向 `frappe.listview_settings[doctype]` 注册格式化器；但 frappe 打开某张列表时会**懒加载**该单据自带的 `*_list.js`（如 DocType 列表的 `doctype_list.js`），其中的 `frappe.listview_settings["DocType"] = {...}` 是**整体赋值**——把启动期注册的对象连同格式化器一起覆盖。

启动期注册"先到先得"的假设不成立：懒加载脚本永远在后，后写覆盖先写。

## 3. 修复

不再依赖注册时序，改用 `Object.defineProperty` 把 `frappe.listview_settings` 上的目标键改造成访问器属性：

- **get**：返回内部存储的配置；
- **set**：核心脚本任何时机整体赋值时，自动把我们的翻译格式化器**合并**进新对象再存储（若核心已定义同名格式化器则尊重核心）。

无论加载顺序如何，格式化器都不会丢。

## 4. 经验教训

- 对 frappe 全局注册表（`listview_settings` 等）做增强时，**必须考虑核心脚本懒加载后的整体赋值覆盖**，用访问器合并而非一次性注册。
- 前端定制的验证要以"打开真实页面看效果"为准，脚本加载成功 ≠ 生效。
